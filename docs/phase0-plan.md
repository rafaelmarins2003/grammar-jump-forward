# Phase 0 — Plan and Gate 0 definition

Pre-registered 2026-09-10, before any measurement. Changes after data exists go in a dated
"Amendments" section at the bottom, never as silent edits.

Goal: decide, cheaply and before any engine C++, whether jump-forward has enough ceiling (Gate 0),
a plausible speedup, and no obvious quality cost. Everything here runs in Python against the pinned
llguidance 1.0.1, HF tokenizers and unmodified llama.cpp binaries.

## Tasks

### P0.1 — How llguidance computes forced tokens

Read the implementation behind `llg_matcher_compute_ff_tokens` in
`~/llama.cpp-jf/build/llguidance/source`. The Python package (1.0.1) exposes the same operations on
`LLMatcher`: `compute_ff_tokens`, `compute_ff_bytes`, `validate_tokens`, `try_consume_tokens` and
`rollback` (verified 2026-09-10). Comparing `compute_ff_bytes` with `compute_ff_tokens` at the same
state shows directly how many forced bytes the token policy leaves unused.

Answer in `docs/notes/llguidance-ff-tokens.md`:
- Which tokenization does it choose for forced bytes (greedy, canonical re-tokenization, something else)?
- How does it treat the last forced token before a free region (the P2 boundary issue)?
- Does it return a conservative prefix, and when does it return 0 tokens?
- Is it defined across a lazy-grammar trigger?

This decides whether "llguidance native ff" becomes policy **PL**, evaluated alongside P1/P2/P3.

### P0.2 — Prior-art check

Before any novelty claim, read and summarize in `docs/notes/prior-art.md`:
- DOMINO, "Guiding LLMs The Right Way" (Beurer-Kellner, Fischer, Vechev, ICML 2024): token
  misalignment under constrained decoding. Does it already measure RQ1?
- guidance token healing
- SGLang compressed FSM / jump-forward: how it handles re-tokenization after a jump
- XGrammar: does it expose or use jump-forward strings?
- llama.cpp Discussion #5455 and Issue #23184: current state

The output is one sentence per item: "measured X / did not measure X". RQ1 wording in the proposal is updated accordingly.

### P0.3 — Gate 0: forced-token fraction (RQ3)

**Corpus (fixed now):**
- BFCL v3: `simple`, `multiple`, `parallel`, `live_simple`, `live_multiple`, using the reference
  calls in `possible_answer/` where available
- Hermes FC v1: `func-calling-singleturn.json`

**Serializations of each reference call:**
- S1: compact canonical JSON (`separators=(",", ":")`)
- S2: default JSON (`", "`, `": "`)
- S3: the target model's own serialization, generated by Qwen3-8B Q4_K_M under the stock tool-call
  path at temperature 0. This one is a GPU job; ask before running it.

**Grammar variants:**
- G1: llguidance JSON schema, default options
- G2: llguidance JSON schema with whitespace fixed to the serialization being measured
- G3: llama.cpp's own `json-schema-to-grammar` output (stock, flexible whitespace), converted with
  `llguidance.gbnf_to_lark`. First check the conversion on a sample: it must accept and reject the same
  strings as llama.cpp's GBNF engine. If it isn't faithful, report G3 as "not measured" with the reason.
  Don't substitute.

**Tokenizers:** `qwen3` is primary. `llama-3.1`, `mistral-v0.3` and `gemma-3` are reported for RQ2.

**Metric:** walk each serialized call token by token through the matcher. Forced fraction =
(tokens obtainable from `compute_ff_tokens` at the point they occur) / (total tokens of the call
body). Report per dataset subset, per schema, and as a distribution (median, p10, p90), not just the mean.

**Threshold (from the proposal):** the median forced fraction on the primary tokenizer, under the
best realistic grammar variant (G1 or G2) with S2 or S3, must be **≥ 25%**. Below that, abandon or
retarget to a higher-determinism DSL. Report G3 in any case: if G3 is near zero and G2 passes,
the engine plan must include a whitespace-canonical tool-call grammar, and RQ1 must test its
effect on quality.

**Tokenizer parity check:** for a 200-call sample, compare HF tokenization against llama-server
`/tokenize` on the Qwen3 GGUF. Any mismatch is reported, and offline numbers for that tokenizer are
flagged.

### P0.4 — Pass-cost curve

How much does processing N tokens in one batch cost compared with one decode step, on Qwen3-8B Q4_K_M,
at context depths near real tool-call prompts (e.g. 1k and 4k)? Use `llama-bench` from `~/llama.cpp`
with prompt sizes 1, 2, 4, 8, 16, 32 and a context depth option (check `--help` at the pinned
commit), `-fa 1`, all layers on GPU, ≥ 5 repetitions. GPU job; ask before running.

Combine with P0.3: estimated decode-time speedup per call = passes without jump-forward /
(passes with jump-forward, weighted by batch cost). Report decode-only and end-to-end, with measured
prefill time included.

### P0.5 — RQ1 emulation design (no engine changes)

Design only; it runs after Gate 0 passes. llama-server accepts prompts as token-id arrays, so a
forced tokenization can be injected exactly:
- natural arm: the model generates the call itself; its tokens are recorded
- forced arm: the same prefix up to each free region, with forced spans re-tokenized by policy
  P1/P2/(PL); the model then generates the value
- metric: argument-value exact match and BFCL `possible_answer` accuracy, paired per call

### P0.6 — Early RQ4 signal

On the S3 generations, measure draft acceptance (Qwen3-0.6B, `--spec-type draft-simple`) separately
on grammar-forced and free positions. If the draft already accepts forced positions at ≥ 95%,
jump-forward's marginal gain over draft speculation is mostly the draft's own cost. Say this early.

## Deliverable

`docs/gate0-report.md`, generated from `runs/` manifests (no hand-typed numbers), ending with one of:
**go**, **go with whitespace-canonical grammar**, **retarget**, **abandon**.
